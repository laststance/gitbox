# Design: A repository keeps its note, links and comment after its card is gone (Issue #216)

Generated by /office-hours on 2026-10-14
Branch: main
Repo: laststance/gitbox
Status: APPROVED
Mode: Builder

## Problem Statement

Issue #216 (filed by the owner, 2026-10-10): the note, links and comment entered for a repository should survive when the repository leaves its board. After an accidental removal, typing them again is tedious, and the services that were linked may be forgotten for good.

Today every way a card leaves GitBox deletes them, because `projectinfo.repo_card_id` is `NOT NULL ... ON DELETE CASCADE`:

| Path              | Code                                                   | How `projectinfo` goes                 |
| ----------------- | ------------------------------------------------------ | -------------------------------------- |
| Remove from Board | `deleteRepoCard` (`src/lib/actions/repo-cards.ts:261`) | card deleted → CASCADE                 |
| Delete Column     | `deleteStatusList` (`src/lib/actions/board.ts:143`)    | `repocard.status_id` CASCADE → CASCADE |
| Delete Board      | `deleteBoardAction` (`src/lib/actions/board.ts:583`)   | `repocard.board_id` CASCADE → CASCADE  |
| Delete Account    | `deleteAccount` (`src/lib/actions/auth.ts:115`)        | `auth.users` CASCADE (stays so)        |

Z (undo) covers drags only. Since #213 the one way to set a repository aside is Move to Another Board.

## What Makes This Cool

The repository is the key, and it lives outside GitBox: as long as the repository exists under its name and the user can reach it, GitHub keeps listing it in the Add Repositories picker whatever happens on the boards. Since #215 a repository sits on at most one board per user, so (user, repository) names at most one card. Keyed that way, the memory needs no trash view and no soft-deleted cards: the picker already is the restore UI. Add a repository removed months ago and its Sentry and Vercel links are on the card again. Before that, its picker row says `Saved: note, 3 links, comment`.

## Constraints

- One repository per user across boards: `repocard_unique_repo_per_user` on `(user_id, lower(repo_owner), lower(repo_name))` (#215). The memory uses the same key. Identity stays `owner/name`, case-insensitive; renames and transfers are not tracked (already in TODOS.md from #215).
- A card's `repo_owner` and `repo_name` never change after insert (`addRepositoriesToBoard` is the only writer, `repo-cards.ts:191`).
- The board page reads comments in its single PostgREST round trip, `repocard(<REPO_CARD_COLUMNS>, projectinfo(comment, comment_color))` (`board-data.ts:134`), which relies on the one-to-one FK today.
- A card added from the picker gets its comment from the board's comment state, which is seeded only from `initialData.comments` (`BoardPageClient.tsx:319` → `useCommentState`). `router.refresh()` is reserved to `useBoardServerSync`.
- A push to `main` that touches `supabase/migrations/**` runs `db push` on production at once, while Vercel deploys the same commit. CLAUDE.md's rules for migrations that move data apply: counts only in logs, refuse before the first write, one `DO` block that is a no-op on a second run, dump and manifest before and after.
- A shared board never shows notes, links or comments (`get_public_board` returns none of them). Unchanged.
- PostgREST: v14.17 locally, v14.5 on production (`supabase services`, 2026-10-14).

## Premises (agreed)

1. The note, links, comment and comment color belong to the user and the repository, not to the card. Key: `(user_id, lower(repo_owner), lower(repo_name))`.
2. Remove from Board, Delete Column and Delete Board keep them. Only account deletion erases them. No delete control: to clear a memory, add the repository again and clear it in the Note modal. A memory of a repository the picker can no longer list (renamed, transferred or deleted on GitHub, or no longer reachable with the user's token) cannot be reached that way: it stays, private and never shown, until the account is deleted. Accepted: it is a few kilobytes at most, and the owner can delete such rows by SQL. The dialogs say "kept for when you add them again", which holds for every repository that still exists under its name.
3. Adding the repository again brings them back without a question and without a toast. The picker marks a repository on no board whose memory holds something.
4. This deliberately reverses a rule of #213 and #215: "`projectinfo` has no row without a card and goes with its card", and the Remove dialog's "Adding the repository again will not restore them." Dialogs, SPEC.md, CLAUDE.md and the tests that hold the old rule change with it.
5. Move to Another Board does not change. A shared board still shows no note, link or comment.
6. Out of scope: an Undo for Remove, a Recently removed list, tracking renames and transfers on GitHub.

## Approaches Considered

- **A, detach and re-attach** (`ON DELETE SET NULL` plus a trigger on `repocard` insert that re-attaches the detached row): not chosen. The memory would belong to the card or to the repository depending on its state, and a trigger would write another table on every insert.
- **C, side archive table** (a `BEFORE DELETE` trigger copies the row out, an insert trigger moves it back): not chosen. The memory would live in two tables again, the shape #213 removed, and the copy would run inside the account-deletion cascade, where an insert for a user being deleted can fail on its FK.
- **B, repository memory**: chosen, below.

## Recommended Approach: B, repository memory

`projectinfo` is keyed by the user and the repository and has no card column. A card finds its memory through its repository. Removing a card only deletes the card.

### Database

One migration, merged in the same PR as the code (see Rollout), one `DO` block that drops `repo_card_id` in the same transaction that creates the computed relationship, so the FK and the function never exist side by side:

- Guard, before the first write: count rows that would share a key (expected 0: each row has a card today and cards are unique per user) and read the policies of `projectinfo` (expected the two the migrations define, as in #213). Refuse with counts only and the next step in `DETAIL`.
- Add `user_id uuid NOT NULL DEFAULT auth.uid() REFERENCES auth.users(id) ON DELETE CASCADE`, `repo_owner text NOT NULL`, `repo_name text NOT NULL`, backfilled from the card each row sits on. `update_projectinfo_updated_at` is disabled around the backfill so `updated_at` keeps its value.
- Key column: `repo_key text GENERATED ALWAYS AS (lower(repo_owner) || '/' || lower(repo_name)) STORED`, with `CONSTRAINT projectinfo_unique_repo_per_user UNIQUE (user_id, repo_key)`. A plain column because PostgREST's `on_conflict` cannot name an expression. Writes are PostgREST upserts with `on_conflict=user_id,repo_key` that send `repo_owner`, `repo_name` and only the fields they change (`user_id` comes from its default): a comment edit is one statement that leaves the note alone, with no read-then-insert race. The alternative, SQL functions that take the card id, is not taken: one function per write, each with its own grants in the migrations and in `scripts/e2e-setup-databases.sh`.
- Drop `repo_card_id` with its FK, its unique constraint and `idx_projectinfo_repo_card_id`. No later contract step.
- Policies: the two policies are recreated on `user_id = (select auth.uid())`. The `FOR ALL` one also requires, in its `WITH CHECK`, a card of the user for the repository (lowercased match on `repocard_unique_repo_per_user`): the app writes only through a card, and a signed-in browser cannot store notes for repositories it never placed (eng review R2).
- Computed relationship: a function `projectinfo(repocard)` returning `SETOF projectinfo ROWS 1`, `STABLE`, `SECURITY INVOKER`, `SET search_path = pg_catalog, public` (the repo's convention; about 0.145 ms per card, eng review R5), EXECUTE for `authenticated` and `service_role` only, with the same two lines in `scripts/e2e-setup-databases.sh`, matching on `user_id` and the lowercased names. The embed of `board-data.ts:134` keeps its shape, and `mappers.ts` keeps reading an object or `null`. It is named like the table on purpose: the FK is gone in the same transaction, so the name is never ambiguous, and the deployment that is still live while the migration has run (see Rollout) keeps loading its boards through the same embed string.
- Spike, local stack (PostgREST v14.17, 2026-10-14), the statements above applied by hand to the seeded database: `repocard?select=…,projectinfo(comment,comment_color)` returns an object or `null` per card; after `DELETE` of a card its row is still readable; a `POST` of a card for `TestUser/Another-Repo` (the memory was saved as `testuser/another-repo`) with `select=…,projectinfo(comment,comment_color)` returns the restored comment in the insert's own response; an upsert with `on_conflict=user_id,repo_key` that sends only `comment` and `comment_color` keeps the note; deleting the user in a rolled-back transaction removed the user's rows. Production runs PostgREST v14.5 (`supabase services`) and the E2E shards of `pnpm e2e:parallel` run v12.2.3 (`scripts/e2e-setup-databases.sh`), so the same checks ran again through a `postgrest/postgrest:v14.5` and a `postgrest/postgrest:v12.2.3` container pointed at the same local database: the board embed `board?select=id,repocard(repo_name,projectinfo(comment,comment_color))` (one request) returned each card's comment or `null`, a card removed and added again as `TESTUSER/Test-Repo` (v14.5) and `LastStance/NSX` (v12.2.3) came back with its comment in the insert's response, and the upsert on `user_id,repo_key` kept the note. Fallback if the production check of the embed fails: a second query keyed by repository in `getBoardBundle` and in `addRepositoriesToBoard`; the board then loads in two round trips instead of one.
- Account deletion erases the memory through `user_id ON DELETE CASCADE`. Nothing else deletes it.

### Server

- `project-info-core.ts`: every function keeps taking the card id the browser has, resolves the card (RLS: own cards only) to its repository, and reads or writes that repository's row. Reads go through the computed relationship in one round trip.
- `addRepositoriesToBoard`: restoring needs no code, because the board embed and the Note modal find the memory by repository. The created cards must carry a restored comment (text and color) back to the browser, so the add handler can put it into the board's comment state without a page refresh: `CreatedRepoCard.comment` (the default comment when none), merged by `BoardPageClient` into the comments it passes to `KanbanBoard`; `useCommentState` adopts card ids it has not seen when that prop changes (eng review R1). Skipped repositories make no card and a failed add returns before the callback, so nothing is merged then. Selecting `projectinfo(comment, comment_color)` in the insert's `.select(...)` returns it (seen in the spike: the row existed before the statement).
- `deleteRepoCard`, `deleteStatusList`, `deleteBoardAction`: unchanged.
- Picker data: `getUserRepoPlacements`, which the picker calls on every opening (`useRepoPlacements`), also returns the saved memory of repositories on no board: the identifier (`toRepoIdentifier`, lowercase, compared with the picker's lowercased `full_name`), whether the note is non-empty after trim, the number of links with a URL after `normalizeLinks`, whether the comment is non-empty after trim. A memory with none of the three (a color alone included) is not returned. The extra query runs in parallel with the placements lookup; when it fails, the action still returns the placements with `savedMemories: null` and the picker shows no marks (eng review R3, R4). Any new export of a `'use server'` file is added to `browser-callable-actions.test.ts`.

## Rollout

Amended by the eng review (R9, R8): deploy first, then migrate. One PR holds the migration and the code.

1. Before the merge: `gh workflow disable supabase-production.yml`, so the merge does not start the migration.
2. Merge. Vercel builds and deploys the new code, which runs on the old schema until step 4: boards and notes load through the old FK (the embed string is the same), the picker shows no marks (the memory lookup fails and degrades, R3), and a note save fails with an error that keeps the typed text (R8). A comment edit fails too and goes back to what it was: its typed text is lost (corrected by the pre-landing review; the comment editor has no draft). A removal in this window still deletes the memory, although the new dialogs already say it is kept. So nothing is edited or removed between steps 2 and 3, and open tabs are reloaded after the deploy (their picker expects the old answer of `getUserRepoPlacements`).
3. When the production deployment of the merge commit is live: `gh workflow enable supabase-production.yml` and `gh workflow run supabase-production.yml --ref main`. The run takes about 35 seconds.
4. After the run: the count-only verification query and the manifest comparison, then the real-account check.

The pasteable blocks, with their expected output and when to stop, are in [the rollout runbook](../plans/2026-10-14-issue-216-rollout-runbook.md).

The old deployment never meets the new schema. If the dispatched run fails, nothing changed (one transaction) and the new code keeps running on the old schema as in step 2; fix the migration forward. If the new deployment itself misbehaves before step 3, `vercel rollback` returns to the previous deployment, and the schema is still the old one.

## Open Questions

1. **Drafts.** The `draft` slice is keyed by card id. A draft typed on a card that is then removed stays in localStorage and does not follow the repository. Default: leave it.
2. **Renames.** A repository renamed or transferred on GitHub after removal keeps its memory under the old name; adding it under the new name starts empty. Same limit as #215. Such a memory stays until account deletion (Premise 2).
3. **Empty rows.** `deleteCommentCore` keeps the row. A memory with no note, no links and no comment stays in the table and shows no mark. Default: keep.

## Success Criteria

- Remove a card that has a note, two links and a colored comment, then add the same repository to any board (also with different letter case): the card shows the comment in its color without a reload, and the Note modal shows the note and both links.
- The same after Delete Column and after Delete Board.
- The picker lists the removed repository with `Saved: note, 2 links, comment`. A repository whose memory is empty shows no mark. Repositories on a board stay under "Already placed elsewhere".
- Another user can neither read nor write the memory (checked as each user, as in the #213 rehearsal).
- After account deletion no `projectinfo` row of the user remains.
- `move-to-another-board.spec.ts` passes unchanged. A shared board shows no note, link or comment.
- The board page still loads in one PostgREST round trip.
- Production migration: the manifest after the run equals the one before for every existing row (id, content hash, `updated_at`), and each row carries the user and repository of the card it sat on.
- Checked on local and on production as `ryota-murakami`, on a board with cards in at least two columns. Remove, Delete Column and Delete Board run on scratch boards only on production.

## Implementation notes

What the implementation found that this design did not say (2026-10-14):

- **The Assignment, run on production (count-only, read-only, 2026-10-14):** 10 `projectinfo` rows, 7 with a note, 7 with at least one link, 5 with a comment, none empty; all 10 held by 1 user, the owner (`ryota-murakami`), so the single-PR rollout's precondition holds. 50 cards on 6 boards, no repository key held by two rows, the 2 policies of the migrations, links stored as JSON arrays.
- **Rehearsals with Supabase CLI 2.120.0 on a local copy of production's public data:** the schema of production equals the one built from the migrations; the manifest (id, user, repository key, content hash, timestamps) is identical before and after for all 10 rows; a second run prints its notice and changes nothing; deleting the user deletes their rows (rolled back). With an extra policy on `projectinfo`, and with a row without a card, the migration refuses, prints its `DETAIL` and changes nothing.

- **Delete Column left its cards in the store.** The Redux store kept the cards of a deleted column until a reload, so the picker hid their repositories as on the current board and the flow "Delete Column, then add the repository again" failed on the same page. `useStatusListDialog` now dispatches `removeStatusListWithCards`, which drops the column and its cards. This was half of the TODOS.md item "Keep Redux in step when a column is deleted"; the other half (late picker notices) stays there.
- **The account-deletion cascade is not an E2E test.** The E2E shards answer `/auth/v1/*` with mock responses, so a test cannot create or delete an account there. The cascade (`projectinfo_user_id_fkey`, `ON DELETE CASCADE`) is checked by the verification query of the migration (`confdeltype = 'c'`) and by deleting a user in a rolled-back transaction on the rehearsal database.
- **Seed links without `type`.** The seed rows keep links as `{ title, url }`, a form the Note dialog drops (production holds none). The picker counts links after the same normalization, so the E2E spec gives `laststance/nsx` one `{ type: 'npm', url }` link of its own.
- **The Note dialog stores an editor document, not text.** A note is saved as the JSON of the editor's document, so a note the user emptied, or never typed while adding a link, is a paragraph without text and not an empty string. The picker reads the note as a document (`isSlateValueEmpty(parseSlateValue(note))`) before calling it saved; measuring the string would have marked a link saved alone as "note, 1 link" (found by the pre-landing review; production held no such note).
- **A card the user cannot see is no empty note.** The memory outlives its card, so `getProjectInfoCore` answers a card that is gone (removed in another tab, an expired session) with "Card not found", and the Note dialog stays closed instead of opening an empty editor over a note that still exists. The card read before a write tells a missing card from a failed read, and Delete comment filters on the board owner as well as the repository key, whose value every user holding the repository shares.
- **Lock order.** The migration locks `repocard` and then `projectinfo`, both ACCESS EXCLUSIVE, before its first statement: dropping `repo_card_id` drops its foreign key, which locks `repocard` anyway, and taking that lock late could deadlock with a board read waiting on `projectinfo`.
- **A comment map that changes identity every render never settles.** `useCommentState` adopts a new `initialComments` object during render, and `KanbanBoard` passed `initialComments ?? {}`: the story without comments re-rendered until React stopped it. The default is now one module constant.
